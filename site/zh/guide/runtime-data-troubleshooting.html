按数据链路排查运行问题 ​

数据来源、工程配置、开发验证、运行部署和用户页面是不同环节。遇到“AI 改好了但线上没变化”，先定位断在哪一段，不一次性重做全部配置。

开始前记录组织、工程、运行环境、模式或版本、发生时间与具体对象。只读检查优先；重启、替换、停用和删除先取得授权并安排影响。

1. 先确认在看哪套内容 ​

  • 编辑器、数据中心和开发预览主要用于当前开发配置。
  • 生产部署使用所选工程版本；开发模式部署也使用提交时构建的快照，不是浏览器实时源码。
  • 修改和保存配置不会自动更新旧部署，“重新部署”也不自动采用最新内容。

在部署详情核对实际模式、版本和环境，再检查是否确实执行了新版本发布与更新部署。

2. 从源头逐段检查 ​

环节到哪里查先看什么
数据来源数据中心 → 接入源或工业采集正确连接、查询或订阅、授权、设备/服务状态与真实样本
数据点数据中心 → 数据点 → 查看详情完整路径、来源、类型、质量、值来源和时间
计算数据中心 → 计算单元输入点、脚本、输出、触发、启用；调试是否保存后进行
报警数据中心 → 报警单元输入点、类型、单位、阈值、延时、死区、恢复条件与启用
版本工程管理 → 发布工程本次配置是否进入构建成功的工程版本
部署运维管理 → 工程部署使用的模式与版本、节点、引擎健康及任务进度
页面访问环境访问入口或节点直连实际开关、地址、入口节点、证书和工程用户角色
历史数据中心 → 历史存储及对应运行服务继承策略、目标、样本触发、保留期和查询时间范围

当前值有数字，但来自默认值、配置预览或陈旧观测时，不能作为链路正常的证据。

3. 常见现象怎样分流 ​

SQL 有结果，数据点没有 ​

回对应连接检查保存查询、输出配置及是否主动生成点。只运行一次 SQL 不会自动完成整条配置，见SQL 数据点。

计算试运行正确，输出点不变 ​

试运行不写输出点。继续查实际运行部署、计算引擎、触发和输入更新，不为刷新值反复点试运行。

数值越限，但没有看到现场报警 ​

先核对是否看同一环境的运行值、类型与单位，规则是否进入该部署，报警引擎是否健康，以及延时、死区和质量是否让判定暂停。

试算匹配不等于现场已经触发；没有新数据或输入质量异常时，也不能直接判断报警引擎故障。

已有报警，但没有收到通知 ​

检查规则的通知继承或单独设置、渠道启用、认证、网络和发送结果。获准后单独测试渠道；通知测试不替代真实触发和恢复链路验证。

页面正常，另一用户无数据 ​

核对工程用户与角色、点位调用权限及登录身份。开发人员的预览身份不等于普通运行用户，复制点路径不会授予权限。

工程显示运行中，但地址打不开 ​

分别检查引擎健康、入口方式、入口节点、端口、路由、证书和网络。工程运行中与入口可访问不是同一状态。

当前值有更新，却查不到历史 ​

先查实际保存策略、来源与单点例外、部署内容、存储目标、样本写入和时间范围。历史不是自动备份，也不会把按需查询自动变成持续采样。

4. 查看运维记录与有效观测 ​

到运维记录按对象、环境和时间筛选，区分已受理、执行中、完成及失败，阅读执行明细。

节点在线不等于所有驱动与运行资格都合格；旧的绿色状态不代表最新观测。加载失败或更新中断时，先重新读取，不反复提交操作。

5. 不要用破坏性操作试错 ​

  • 不以重建基础服务、清库或删除环境刷新页面，它们可能清空数据。
  • 活动报警未恢复时，不随意停用或删除规则，避免失去清警路径。
  • 不靠关闭证书校验、共用管理员或分享密钥解决权限与连接问题。
  • 不把删除开发源码、对话、点位或部署当作同一种“重置”。

求助时提供对象、版本、环境、时间、错误和已核对步骤，敏感凭据留在安全渠道。
