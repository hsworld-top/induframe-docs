网络与端口清单 ​

本页供服务器维护人员和网络管理员查询。普通使用者先看配置网络与防火墙，不必先理解集群内部端口。

规则要写在正确的目标服务器上：入站是别人连接进来，出站是本机连接出去。每条规则记录来源、目标、协议、实际端口及用途；返回流量也要符合所在网络的规则。

入口端口以实际配置为准，默认值不是固定要求。 中心管理端口在安装时可自定义；环境入口和独立入口由各自页面设置。修改过的端口替换本页示例中的默认值，不要新旧端口一起开放。

用户访问入口 ​

谁连接 → 连接到哪里端口允许范围
平台管理员 → 中心管理地址默认 18100/TCP，HTTP可信管理网络；路径含 /admin/，不映射公网
平台使用者 → 中心公共地址当前交互安装默认 443/TCP，HTTPS实际需要使用平台的来源，可仅限企业内网或 VPN
工程使用者 → 环境入口所在节点页面中设置的环境入口 TCP 端口需要使用该环境下工程的人，保留完整工程路径
工程使用者 → 独立部署所在节点工程部署中设置的独立 TCP 端口仅在启用“节点直连”时需要
维护人员 → 被管理服务器实际 SSH 端口，常见 22/TCP指定管理来源，修改其他规则前先保留此通道

只使用环境入口时，不需为每个工程另开独立端口。同一台服务器上的端口不可随意重复占用；页面允许填写的 1024–65535 不是应整体开放的范围，也不需要为了这些入口放行整个 30000–32767。

交互安装当前使用 HTTPS。技术部署资料中的 HTTP 18101 不是所有用户都应额外开放的端口，实际以本次安装结果为准。

中心与接入节点的后台通信 ​

先按一台中心、两台节点的例子分清机器，再按下面的顺序设置。只增加一台节点时，“其他节点”这一项暂时不用填写。

本节按当前中心 IPv4 安装方式及默认跨节点网络整理，不是公网开放清单。“允许谁连接过来”就是防火墙或安全组里的来源，填写这些服务器的实际内网地址。协议字段按表分别选择 TCP 或 UDP，不能只填同一个端口号就认为两种通信都已允许。

第一步：在中心服务器设置 ​

打开中心的主机防火墙和对应安全组，只允许已确定要接入的节点来源。以下按中心提供内置仓库和校时服务说明；中心下发了其他实际地址时，在对应服务所在机器上配置，不把规则一律加到中心。

允许谁连接过来中心接收的协议与端口它让节点完成什么
每台接入节点实际公共入口端口，默认 443/TCP联系平台、登记和发送心跳，使用节点安装包提供的中心地址，不使用管理入口代替
每台接入节点6443/TCP加入集群，成为能一起工作的服务器
每台接入节点实际仓库端口，默认 5000/TCP下载运行所需的镜像；镜像可理解为准备好的程序包
每台接入节点123/UDP对齐时间；校时服务本身也须允许这些来源
每台接入节点8472/UDP让中心与节点上的运行程序跨机器通信
每台接入节点10250/TCP读取节点状态指标，供运行监测使用

仓库连接还涉及证书和权限。只开放端口不代表镜像一定能下载；遇到证书错误时核对中心下发配置，不改成明文或跳过验证。

第二步：在每台节点设置 ​

在各自节点的防火墙和安全组操作。中心也参与节点间通信，第一步的最后两项不能漏掉。

允许谁连接过来这台节点接收的协议与端口用途
中心和其他已接入节点8472/UDP运行程序之间跨机器通信，只允许本集群成员
中心和其他已接入节点10250/TCP节点状态指标，只允许实际集群成员和另行批准的监测来源

例如只有中心、节点 A、节点 B 时：A 的来源填写中心和 B，B 的来源填写中心和 A。新增加节点后，还要更新原有机器的允许来源；不预先信任所有内网服务器。

如果出站也受到限制，按实际连接方向核对出口、去程和回程。其他节点不需要为了加入集群，就把自己的管理、仓库或工程访问端口一并开放；工程入口另按实际部署配置。

第三步：用实际结果复核 ​

先查看节点的连接、最近心跳、时间同步和运行资格相关提示，再请维护人员确认实际集群加入、镜像下载与跨机器运行。不要把某一个状态正常当成整组网络已经通过。

  • 节点已在线，但加入集群未完成：先核对到中心 6443/TCP 的连接及加入结果。
  • 已加入但运行程序下载失败：先核对中心下发的仓库地址、实际端口、证书和权限。
  • 各机器单独正常，但跨机器运行有问题：先核对 8472/UDP、内部转发和所用网卡，不连续增加无关端口。
  • 时间同步异常：核对指定校时服务、123/UDP 和服务端允许来源。

这些是排查起点，不是仅凭现象就确定故障原因。TCP 连接测试不能代替 UDP 校时或跨机网络核验，UDP 测试没报错也不代表服务已正常。后台敏感端口应从非白名单的受控来源复核拒绝效果，不只验证允许的一侧。

当前普通接入不需要向外开放 2379–2380/TCP，也不因为使用 K3s 就开放 51820–51821/UDP 或 5001/TCP 等可选功能端口。增加接入节点不等于本产品已具备或已验证高可用部署。

内部网络与不应外露的服务 ​

  • 当前容器网段为 10.42.0.0/16，服务网段为 10.43.0.0/16。必须与企业、VPN、设备及其他集群网络错开；用户电脑通常不需要直接连接这些地址。
  • 保留防火墙时，维护人员还应核对这些内部网段的来源与转发策略；不能只加普通主机入站规则，也不能一概放开全部转发。
  • 内部 API、数据与计算服务的 18101、18102、18103，以及内置数据库、缓存、消息和对象服务的 5432、18379、1883、8333，不是供用户逐个访问的公网端口。
  • 编辑器、AI 和页面预览使用平台提供的代理入口，不把每个开发进程的内部端口映射出去。
  • 安装器会准备运行环境所需的容器网络规则，但不等于替用户配置好了 UFW、云安全组或机房防火墙。

K3s 通用规则可参考官方网络要求，实际仅采用本产品启用的功能与现场需要的范围，不照搬整张通用开放表。

Ubuntu 24 的 UFW 入口示例 ​

以下仅演示用户入口规则，不是一套可直接启用的完整集群防火墙策略。它们不替代前面的后台通信、内部转发及业务出口核对，也不代表现场 UFW 与安全组组合已经验证。

操作前先确认

命令由维护人员在目标服务器终端执行，示例 IP 都是虚构地址，必须先替换。保留当前 SSH 会话及可用控制台，先允许自己的实际 SSH 来源和端口，不清空已有规则。

平台部分端口由容器转发提供，可能不经过普通主机入站规则。UFW 的单条来源限制不能作为已隔离证明；还要设置上游防火墙或云安全组，并从允许、拒绝来源两侧核验。已有全来源允许规则也不会被新规则自动撤销。

先查看，不急着启用 ​

bash
sudo ufw status verbose
sudo ufw status numbered
sudo ufw show added

active 表示已启用，inactive 表示未启用；没有 UFW 也不代表没有其他防护。先记录原有规则与默认策略，已有其他业务时不要直接更改全局策略。

中心服务器示例 ​

假设中心为 10.20.0.10，管理网络为 10.30.0.0/24，平台使用者网络为 10.40.0.0/24，SSH 端口为 22。/24 表示一个网段，只允许一台管理电脑时可改成它实际来源 IP 的 /32。

先允许 SSH，再允许管理与平台入口；在中心服务器执行自己核对过的对应规则：

bash
sudo ufw allow proto tcp from 10.30.0.0/24 to 10.20.0.10 port 22
sudo ufw allow proto tcp from 10.30.0.0/24 to 10.20.0.10 port 18100
sudo ufw allow proto tcp from 10.30.0.0/24 to 10.20.0.10 port 443
sudo ufw allow proto tcp from 10.40.0.0/24 to 10.20.0.10 port 443

上述目标是中心的示例内网地址。如果入口实际上使用其他网卡地址，维护人员须针对真实目标配置；来源也按服务器实际看到的地址填写。

环境和独立入口示例 ​

假设环境入口在 10.20.0.11，端口为 17800；需要让 10.40.0.0/24 的使用者访问，则在这台入口节点添加：

bash
sudo ufw allow proto tcp from 10.40.0.0/24 to 10.20.0.11 port 17800

如果某个工程还在 10.20.0.12 启用了独立端口 17810，才在这台独立部署节点另外添加：

bash
sudo ufw allow proto tcp from 10.40.0.0/24 to 10.20.0.12 port 17810

两个端口都只是例子。不要把规则全部加在中心服务器，也不要为未启用的独立访问预先开放一批端口。

规则生效与复核 ​

UFW 已启用时，新增规则通常立即生效。原先未启用时，只有完整核对 SSH、其他业务、节点后台通信与内部转发，并确保控制台能够恢复之后，维护人员才启用：

bash
sudo ufw enable
sudo ufw status verbose

保留原会话，另开终端建立新的 SSH 连接；再从真正的使用者电脑打开页面，并从非白名单的受控测试来源验证敏感端口无法访问。不能只测服务器自己，也不能把规则保存成功当成访问验收。

改端口、删除节点或卸载后，按用途记录清理自己的 UFW 与安全组规则。使用编号删除时每删一条就重新查看，因为编号可能变化；不批量清空，不误删 SSH、共享集群或其他服务的规则。

连接外部数据库、设备和 AI 时 ​

多数接入源是平台中的程序向外连接目标服务，不是让外部服务器连接进平台。不能把数据库连接失败误处理成在中心开放数据库端口。

要使用的外部服务常见目标端口示例由谁确认
MySQL、PostgreSQL、SQL Server常见 3306/TCP、5432/TCP、1433/TCP数据库管理员提供实际地址、端口、账号及允许来源
Redis、MQTTRedis 常见 6379/TCP；MQTT 常见 1883/TCP 或 TLS 8883/TCP以接入源配置和外部服务的实际监听为准
Kafka常见 9092/TCP，实际可能不同引导地址与返回的各消息节点地址都要能解析、访问
HTTP、WebSocket、TDengine按实际 URL；常见 80/TCP、443/TCP，TDengine REST 常见 6041/TCP只连接配置中的目标服务，不根据协议名称猜另一组端口
工业设备按驱动与设备设置；如 Modbus TCP 常见 502/TCP、OPC UA 常见 4840/TCP现场设备负责人确认协议、目标及权限
AI 模型服务常见 HTTPS 443/TCP；自建服务按实际端口确认开发环境能到达模型地址，DNS、证书、API Key 和必要代理正确
DNS 解析服务53/UDP 与 53/TCP使用组织批准的解析服务，主机与容器都要能正常解析

这些是常见值，不是必须全部放行的列表，也不扩大已测试的数据库、设备或模型兼容范围。使用了哪一种，才允许相应程序到那个实际目标。

发起连接的位置可能是采集节点、开发容器或运行容器。远端看到的来源还可能经过出口地址转换，须由网络管理员确认，不把使用者电脑或某个容器地址直接猜填到远端白名单。

域名、证书和目标权限也要一起核对；电脑浏览器能访问模型或数据库所在网络，不代表服务器里的程序也能访问。限制出口时按具体服务和组织批准的出口方式处理，不放开整个互联网来解决一次失败。
